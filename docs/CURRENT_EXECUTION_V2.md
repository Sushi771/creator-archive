### 一、必须实现的产品目标

我要的是类似 WeWe 的使用流程：提供公众号或小红书博主链接，识别并订阅该博主，后台刷新内容，保存到自己的资料库，再按博主一键导出。

小红书必须包括：
1. 首次同步该博主全部可获取历史内容，保存正文、全部可获取图片及视频，而不只是作品编号、标题或封面。
2. 后续刷新新增内容，复用已保存资料，不每次重新下载全部历史。
3. 支持单个、所选和全部已确认订阅博主的更新、下载及按博主导出；操作范围不能被前端当前页限制。
4. 支持持久检查点、去重、暂停和恢复，显示每个博主的实际进度、失败原因与内容缺口。
5. 支持本地阅读和原有 Markdown、离线 HTML、媒体及结构化数据导出，供 Obsidian、AI 分类总结等使用。

公众号保留同样的订阅、更新和归档目标；实际来源未恢复或不支持历史时，明确保留缺口，不能降低需求后宣布完成。

“全部可获取”指来源真实允许访问的范围，不包括突破私密、删除、权限或平台限制。只能返回最新几篇的来源可以用于增量，但不足以完成全历史需求。原始博主全历史、来源当前可见范围和本地已有资料必须分开说明。

首次历史同步、日常增量更新、导出本地已有资料是三种不同操作。后台分页本身允许；不允许把正常全量功能改成只有五篇、只有首页或单篇下载器。

### 二、先纠正已落地的错误限制，保护已有成果

保留现有前后端、FastAPI、SQLite、归档、媒体、安装器和运行脚本。检查现有实现再补缺口，不换框架重写。固定安装目录用于运行，不直接在那里开发。

读取 AGENTS.md、PROJECT_STATUS.md 顶部、最近 CHANGELOG，需求和研究文档按需读取。把这份任务书保存为唯一的最新执行说明，并在项目指令中引用；旧任务书标记已被替代，历史证据保留。

检查代码、配置、UI、文档和交接中是否已有以下错误限制，逐项撤销：

- 因五篇验收而禁止正常历史分页、限制总图片数量、禁止正常视频下载。

- 将公众号 WeWe 修复完成视为整个 Creator Archive 开发的前置条件。

不要把正常的分页大小、串行处理、退避、超时、缓存、去重和暂停控制误删。撤销总量限制不等于无限并发、无限重试。

禁止破坏性重置、清理工作树、强推、覆盖未提交改动或默认删库重装。涉及旧库和目录变更时先备份，在副本验证升级与恢复。旧固定实验不擅自扩展；新正式同步复用有效资料和可兼容检查点，不要求用户删除旧库。

### 三、技术路线：后台订阅取数，不持续操控浏览器翻阅

用户排除的是用浏览器持续滚动主页、逐篇打开详情、重启后重新滚动整条历史来恢复的正式采集流程，不是禁止一切后台 HTTP 请求。

允许评估成熟项目的后台 HTTP、RSS、Atom、JSON Feed、接口和必要会话能力。浏览器可以用于必要的一次登录授权、本人验证或本地界面测试；后续内容获取应由可维护的后台来源完成。

不要仅凭“DrissionPage＋登录”就排除项目。查实际代码：Session/HTTP 取数与浏览器持续导航是不同实现。反之，headless、远程浏览器或服务端浏览器仍是浏览器，不能换个名称就说路线已改。

默认不再调用旧 XhsBrowserTransport 的滚动、逐篇 goto 和历史重放能力。新来源失败时明确报错，不能偷偷回退到旧方式；旧代码和证据可保留，不作为正式默认来源。

RSS/API 只是接入或输出形式，不保证上游没有自动取数，也不保证账号安全。必须核查上游实际怎么获取内容、使用谁的账号、是否反复取旧内容、能否持久缓存及恢复。不能把第三方接口称作官方授权接口，也不额外规定只能用官方开放 API 而放弃其他可评估方案。

使用本人已授权的来源和会话，不擅自购买服务、发送凭据给第三方、轮换账号/IP或绕过验证码、访问拒绝和账号限制。密钥只放私有配置，不进入 Git、公开 CI、截图、日志或导出。

### 四、公众号：参考 WeWe，但不依赖一个尚未修好的实例

wewe-rss-ss 仍在修复。用户要参考其“订阅—后台刷新—入库—按博主导出”的流程及实现，不是认定它目前已经恢复可用。

只读查看该仓库最新 README 顶部、docs/DEVELOPMENT_HANDOFF.md、实施任务书及 Provider/Feed/导出代码，以最新实现为准，不把旧成功介绍当现状。

Creator Archive 实现可替换的来源配置，支持已核实的 RSS/Atom/JSON Feed/API 接入。WeWe 是可选来源之一，恢复后可以接入，不应成为硬编码的唯一依赖。

不要重复修复 WeWe 旧中转、另造一套相同登录系统、改写它的生产库、修改其配置或重启其服务，不干扰另一个修复任务。两个项目不共享可写 SQLite，不同时触发同一账号的重复刷新。

WeWe 未就绪时，完成本项目连接、缓存、界面和隔离联调，继续小红书及其他必要工作。真实公众号来源未接通就明确标记未接通；不以模拟成功冒充公众号恢复。

分清请求刷新、上游接受任务、上游取得新内容和本地入库四个状态；HTTP 200 不等于内容已经同步。查清 update=true、fulltext 和添加订阅等入口是否隐式访问原站，避免反复触发。

核查 Wechat2RSS 等候选的实际历史能力。只支持最新内容、保留已收录文章或读取上游旧缓存，不等于能够补齐订阅前全部历史。缺少历史能力时保留独立缺口，不停止其他工作，也不宣称需求完成。

### 五、小红书：优先复用已有项目，查清全历史能力

优先定向核查以下参考，不为重复调研拖延实施：
https://github.com/DIYgod/RSSHub
https://github.com/yllhwa/RSSWorker

RSSHub 重点看 lib/routes/xiaohongshu/user.ts 和 util.ts。此前审阅线索包括后台 HTTP 分支、浏览器回退以及批量并发获取正文；执行时核查最新版本。可以依许可证复用适合的解析、媒体和订阅结构，但要避免默认浏览器回退与无界并发。

RSSWorker 重点看 src/lib/xiaohongshu/user.js。此前审阅版本主要是主页标题和封面，没有完整正文与历史分页，且使用标题作 guid。可参考轻量实现，不能把摘要源说成全文归档，也不能照搬标题作为唯一标识。

上述只是参考，不是已验证可用的最终方案。必须查清：目标作者识别、当前列表、历史分页、正文、图片、视频、增量更新、账号依赖、许可证及维护状态。只有近期 Feed 而无历史接口时，应另找兼容历史来源或明确无法满足的具体环节，不能把整个产品降为近期订阅器。

已有候选不足时允许针对明确缺口继续定向找成熟项目和修复，不把“只看两个项目”变成卡死条件；但不要无限扩展选型或重写大型采集框架。普通技术选择自行决定，记录采用理由和剩余问题即可。

对包含 DrissionPage、Playwright 等依赖的项目，根据实际数据通路判断，不能只看依赖名称。后台接口取数可以评估；将同一浏览器批量导航藏在远程服务后不算替换完成。

沿用现有模块边界做最小来源适配，不另造复杂插件平台。必要时将增量源与历史源分开接入，但必须用稳定平台、作者和作品 ID 对齐，并保留各自覆盖证据。

### 六、完整同步、增量和导出如何工作

正常首次同步应按明确订阅范围，后台逐批获取全部可获取历史，直至来源给出可信结束证据或遇到需处理的外部阻塞。没有五篇总量限制，不逐页要求用户确认。

串行或有界低并发处理，遵守来源限制，保存游标、已完成作品、正文及媒体状态。暂停或中断后尽量继续未完成部分，不重抓全部成功内容；历史游标失效时查清原因，不能无期限从头重扫。

使用稳定平台/作者/作品 ID 去重，保留经核验的原文来源。昵称、标题、数组位置或临时访问参数不能作为唯一标识。所有入库内容都做作者归属校验，不是只有抽查五篇才校验。

日常增量根据可靠排序、更新时间和已保存作品判断新增与变化。考虑置顶、改文和重复返回，不能随意遇到一条重复作品就认定后面没有新增。

正文、图片、视频分别记录保存结果，成功资源复用，只补缺失或确有变化的部分。不能用作品列表数量代替完整正文或媒体数量。

单作者失败与其他作者隔离；但同一平台出现限流、安全验证或账号异常时，暂停该平台相关请求，保留进度，不轮询试探或换账号/IP。普通暂时网络故障采用有上限重试和退避，不无限重试。

显示任务范围、阶段、最近进展时间、已发现作品、已保存正文、媒体成功/失败、来源覆盖与剩余缺口。待确认或已取消的订阅不能被悄悄纳入新批次。

手动更新可用，定时功能可配置。未配置的真实定时任务默认关闭，不自行选一个频率开始长期采集；不因此阻止已授权的正常首次完整同步。

导出单个、所选或全部已确认订阅博主的本地已有内容，按平台和稳定作者分目录，包含原有 Markdown、离线 HTML、本地媒体、JSON/JSONL、索引及缺口清单。导出只读本地，不偷偷重新获取原站正文媒体，断网和停止服务后仍可阅读，不覆盖手工笔记。

输入链接与重定向做必要来源校验，外部正文按不可信内容清理，防止脚本执行和访问无关内网。已配置的本人本机上游允许按明确白名单访问，不一概阻断。

### 七、验收：抽查五篇内容，不限制正常同步量

在正常同步所得的小红书内容中选五篇不同笔记，核对它们与所订阅博主是否正确匹配。尽量覆盖不同同步位置和已有内容类型；涉及多位博主时覆盖不同作者，但不为凑样本新增无关订阅。总共抽查五篇，不拆成公众号两篇、小红书三篇，也不要求每位博主另抓五篇。

每篇核对：
- 稳定作者 ID 与订阅博主是否一致，不能只看昵称。
- 作品 ID、原文链接及原站内容是否对应同一篇。
- 标题、正文、图片顺序与视频是否属于该篇，是否串号、串文或附件错配。
- 本地入库、界面展示与导出后归属和内容是否仍正确。

优先使用正常同步取得且可追溯的来源响应、原文证据和本地附件核对，必要时只有限复核这五篇的原文。不能只比对本地数据库和本地导出就说与来源匹配，也不为抽查重新抓取整个历史。

来源实际不足五篇就按实际数量报告；不能编造、抓无关作者或不断更换失败样本凑足成功。发现错配要修复并复查原样本；涉及其他已入库内容时用已有资料排查影响范围，必要网络修复仍应有针对性。

五篇抽查通过，只证明这五篇对应正确。全历史覆盖另用正常同步中的分页链、可信结束状态、去重结果及缺失清单判断；列表完整、正文完整、媒体完整分别报告。超时、页数预算、登录失效、限流、空异常页不能当作历史结束。

分页、去重、恢复、断网、导出、资料升级等代码回归尽量用隔离模拟来源、缓存与临时库。必要测试可以运行，不按测试项数量简单限制，但不要为增加测试数量反复访问真实账号或重复开发边缘功能。

记录正常同步与验收复核各自的请求和下载量，避免重复测试放大访问。这里没有五篇正文上限、十张图片上限、视频禁令或第六篇禁令；保留合理的频率与并发保护，不承诺任何实现绝无账号风险。

### 八、授权、部署与自主执行

在已有授权和来源条件允许时，用户已授权按上述路线对已明确订阅的博主进行正常完整同步、下载、导出及五篇抽查。不逐篇、逐页重复询问，不擅自扩展到未知账号或未确认博主。

确实需要本人扫码、额外权限、付费许可、新第三方接收凭据或新的公网发布时，一次性说明最少必要事项，不能代替用户授权。来源受阻时继续独立必要工作；全部剩余工作都依赖外部条件时保留进度，准确说明缺什么，不反复空转。

沿用现有可运行部署完成更新，核对实际运行版本与源码提交，保留数据、备份及回退。别因为暂时缺少 Docker/WSL 就停止所有应用开发，也别为本轮擅自增加云平台或推翻安装方式。来源地址可配置，为日后个人线上使用保留迁移能力，不自行购买服务器。

这是一个完整任务：核对和纠偏→定向选型→实现来源适配→全量与增量联调→必要测试→正常同步与五篇抽查→部署更新→同步GitHub并交付。主 agent 对最终结果负责，不每做一个小单元就结束并让我复制新启动句。

沿用用户已指定且实际可用的模型与思考强度；不能声称配置了工具无法核实的设置，不因切模型耽误已授权工作。

用户授权为本轮目标进行必要的同项目串行接续，由你自行判断上下文是否需要切换，但不恢复无目标的无限自动接力。

开工时核实实际可用的持续任务、上下文压缩、子 agent、后继任务创建与启动能力。优先在同一任务继续；确需交接时先保存精简状态：目录、分支、提交、未提交改动、来源决定、同步检查点、抽查五篇记录、阻塞与下一步。

只有实际工具能创建并启动后继时，才创建一个并核对任务 ID 和运行状态，移交唯一写入权；不得并发修改同一工作树或重复启动同一真实同步。已有后继则复用，不重复创建。

无此工具就留在当前任务继续，不编造“已自动新开窗口”，不私改 Codex 内部数据库或另造调度系统。硬性额度、权限、登录或运行环境中断必须如实报告，不声称任务结束后仍在后台自行运行。

子 agent 可按模块协作，主 agent 统一调度真实同步，不能各自用账号重复采集。不要为证明自动接续而人为频繁切任务。

### 九、同步要求与最终交付

每个有意义的可验收单元，同步受影响文档、CHANGELOG.md、PROJECT_STATUS.md，做必要测试及差异/敏感项检查，提交并非强推推送 GitHub，核对远端分支与文件。文档保持精简，不每轮复制全部历史；公开 CI 不使用真实账号或资料。

不擅自合并 PR，不以工作树干净为由丢弃改动。更新发布产物时区分源码提交、打包版本和实际运行版本，不只更新文档。

最终报告：
1. 两个平台各自实际使用什么来源，怎样取数，是否依赖持续浏览器，支持哪段历史和哪些正文媒体。
2. 实际可操作的订阅、首次完整同步、刷新、下载、按博主导出入口与运行结果。
3. 正常同步的列表、正文、图片、视频及失败统计；是否有可信历史结束证据，哪些部分尚未完成。
4. 抽查的五篇及作者归属、正文媒体匹配结果；来源证据与是否新增网络复核，不把抽查通过冒充全历史完成。
5. 原有资料保护、实际运行版本、分支、本地及远端提交、必要测试与部署结果。
6. 真正未解决的来源、权限或其他外部条件，以及用户必须做的最少事项；后继任务已实际启动还是当前任务已结束。

不要只交规划、空接口、截图或测试数量。来源确实无法接通时可以交付可运行的部分结果，但必须清楚区分代码实现、模拟通过、真实内容匹配和全历史同步完成。

现在先核对最新基线与已生效规则，撤销错误的五篇采集硬限制，保留安全与资料保护措施，然后按上述目标继续执行。
