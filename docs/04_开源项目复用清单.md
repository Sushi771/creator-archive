## 使用本清单的方法

先读能力边界，再选择复用方式。README 宣称、源码存在、真实样本通过是三个证据等级；本轮新版 WeWe 有源码审查和有限本机 UI 观察，扫码、导出及历史未获真实成功证据。维护活跃、星数多不等于当前接口稳定。固定版本是本次研究基准，不是已决定发布依赖；进入开发时先验证，再锁定。

“复用”优先顺序：已有合法兼容 API → 许可允许的组件/模块 → 有明确缺口时自有实现。接口隔离用于可替换性，不自动免除许可证义务。许可标签仅为源码记录，涉及具体分发/商业使用应按完整条款确认。

## 公众号复用方案

候选 A：保留已有 WeWe 订阅身份和文章记录作为迁移来源；`4f0b426` 的扫码、封面与兜底正文改为直连微信读书，旧中转配置及客户端仍在但这些新路径不发送 token 至旧中转。它的封面接口只能做最新检查，不能为全历史提供逐页 ID、游标或末页。先核实本机扫码/导出及合法可访问的历史来源，再决定最小接入；不得因旧数据库有文章就宣称本版本可重新枚举历史。

候选 B：独立验证 we-mp-rss 的公众号后台模式。它具有分页实现，但需要合适账号权限，默认页数限制必须显式处理。其 weread_mp 文档说明只能取最新一篇，不能承担本产品 P0 历史需求。

Access 作为离线归档与错误状态参考；若以后用户选择微信 PC 模式，再另行讨论系统代理、证书、许可与恢复流程。当前不安装也不改系统设置。

先在同两位公众号上比较 A/B 的历史覆盖、登录寿命、空结果处理、图片视频成功率；一个模式失败不得自动切到只能返回最新一篇的模式并宣称全量成功。

## 小红书复用方案

xiaohongshu-mcp 先验证登录、从作品识别作者、详情获取；其主页读取需补上经验证的历史枚举。XHS-Downloader 可评估媒体和文件续传，但未完成后台作者遍历，且 Markdown 输出不等于完整 Obsidian 图文。

MediaCrawler 的作者分页实现可帮助理解问题边界，但其许可限制不能忽略；不复制受限代码作为默认解决方案。如复用许可允许的浏览器组件实现正常主页翻页，也必须有跨页、末页与重启验证。尚未发现一个经过本轮真实验证、可整包满足全流程的成熟项目。

## 抖音及未来平台

抖音先记录接口与候选，P1实施。Douyin_TikTok_Download_API的v5在功能上贴近，但既有监控和回溯上限会漏历史；应适配它的分页API，自有服务保存游标和完整性。F2可减少服务体积，但需自行提供HTTP/MCP及队列层。避免为多平台预先引入大型分布式部署。

## 必须由产品补齐的共用能力

1. 双平台一致的稳定作者ID与订阅模型，从作品反查作者。
2. 无隐含页数截断的全历史作业；真实末页证据；跨重启游标恢复与增量去重。
3. 所有订阅一键分作者归档，完整性清单与缺失项；内容覆盖、正文、媒体分状态。
4. 同一结构生成离线HTML、Obsidian Markdown和JSONL；原文与AI产物分离。
5. 受控重试、统一节流、真实错误和账号状态；不靠不断点击刷新。
6. 按作者分页读取的最小MCP工具集，明确输出范围与来源。

这些是调研确认的组合缺口。开发前仍需逐项检索选定组件是否已有可用实现，能适配即不重写。
