## 产品目标

用户提供公众号文章、小红书笔记或博主主页链接，应用识别博主并建立订阅；用户可手动更新全部订阅博主的全部可获取历史，再一键按博主下载正文、图片和可获取视频至本地与 Obsidian，形成可用于 AI 分类、总结、文风分析的可追溯资料库。通过独立的工具连接，让 ChatGPT 读取已归档的作者资料。

文档评审已结束，进入技术验证。已建立离线验证骨架；真实双平台方案尚未通过G1。

## “全部”的准确含义

目标是获取当前账号和平台允许访问的全部历史。不能承诺已删除、私密、平台不可返回的内容；也不能把技术限制包装成“全部完成”。记录每位博主的页数、作品数、最早/最新日期、分页终止依据和缺失原因。配置上限、首屏结果、接口异常、登录失效、重复游标都不能标为全历史完成。

内容历史覆盖与媒体下载完整性分别显示。例如“已遍历可获取历史，238 篇中 4 篇缺视频”与“仅扫描 3 页，仍有更多历史”是两种不同状态。原画质定义为保存当前实际可获取的最高档资源且不二次压缩，不承诺取得作者上传原文件。

## 产品与技术方向

- 首版沿用 Windows 本地服务与本地网页界面方案；部署路径和实际操作系统在验证开始前核对。SQLite 与本地文件是主数据源。
- 自有核心负责博主订阅、分页任务与恢复、统一格式、下载清单、搜索和 AI 资料接口；平台登录、详情和媒体能力优先用已验证的开源组件。
- 离线 HTML 用于尽量保留阅读样式，Markdown 用于 Obsidian；图片和视频必须本地化，相对路径可移动。复杂公众号样式不要求 Markdown 像素级复刻。
- 默认不接管微信 PC 的系统代理与证书。普通公众号嵌入视频与视频号卡片分别验收，缺视频须如实显示。
- ChatGPT 工具连接是单独验收项。本地安装成功不等于当前会话已获得平台读取能力；不得以自建连接绕过当前会话已出现的站点安全限制。

## 并行调研后的选择

本次按公众号、小红书、抖音/多平台三个方向并行核查 README、许可证、固定提交源码和公开问题；没有登录平台或运行采集器。详细依据在 04 及 research 附录。

| 平台 | 优先验证 | 已发现的关键缺口 |
| --- | --- | --- |
| 公众号 | 用户的 wewe-rss-ss；对比 we-mp-rss 的公众号后台模式 | WeWe 批量刷新仅第一页；历史另走流程且恢复不足。we-mp-rss 的 weread_mp 模式仅最新一篇，不能用于全历史 |
| 小红书 | xiaohongshu-mcp 的登录/详情；评估 XHS-Downloader 的媒体能力 | 前者主页只读当前加载状态；后者后台作者枚举未实现，主页全量靠浏览器脚本；不能直接兑现订阅全历史 |
| 抖音（后续） | Douyin_TikTok_Download_API；较轻方案 F2 | 前者监控/回溯有条数和页数限制；后者仍需补订阅任务检查点 |
| 对照参考 | Access_wechat_article、MediaCrawler、TikTokDownloader | 分别存在非商业许可/系统侵入性、非商业学习许可、签名不再维护等限制 |

没有选定一个仓库整包直接作为产品。先验证能力与许可，再决定 API 适配、组件依赖或仅研究。发现现成合适功能就复用，只有明确缺口才实现；不得把“独立进程”当作自动消除许可证义务的理由。

## WeWe 故障判断

已核对用户 fork 提交 `4cd64f1`：批量捕获异常后仍正常返回，前端因此可能提示全部完成；刷新只拿第一页；历史状态与任务游标不足以可靠恢复；账号选择与重试缺少统一退避。它们能解释部分“反复刷新”现象，但真实主因仍需部署版本与脱敏日志确认。

此外，默认文章列表服务是 `weread.111965.xyz`，会接收微信读书 Bearer token。新产品必须明确该外部依赖与数据流，不能因本地部署就声称所有请求都在本机处理。上游 cooderl/wewe-rss 已归档，不按活跃维护依赖规划。
