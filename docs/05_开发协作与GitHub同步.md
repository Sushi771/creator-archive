## “实时同步”的执行定义

开发过程中，每完成一个可核验的小工作单元就提交并推送，用户已预先授权，无需每次再询问确认。每次更新都必须同步受影响文档、CHANGELOG.md 和 PROJECT_STATUS.md，文档/接口变化与相应实现同一批提交。开始工作先核对远端，结束一个阶段记录 commit SHA、分支、变更、验证结果和剩余事项。不等项目全部完成才第一次上传；不得强推或覆盖远端新提交。

它不是逐按键上传，也不是本轮结束后仍有后台代理持续运行。若网络/权限导致失败，保留本地工作并明确“尚未同步”，恢复后先比较远端再推送；不得覆盖他人更新或强推隐藏冲突。

每条提交备注至少写明：为何修改、修改内容、同步文档、已做验证、未完成或受限事项。纯实现细节未改变需求时，也要在更新日志说明“需求和接口不变”及验证结论。验证未执行写明原因，不以“已测试”笼统替代证据。当前提交的 SHA 由 Git 自身记录；更新日志以日期/版本和提交标题对应，避免在同一提交中自引用尚未生成的 SHA。

建议 `main` 保持可审阅基线，功能使用 `feat/...`、修复使用 `fix/...`、文档使用 `docs/...`；按任务提交并创建PR。仓库公开不等于已选择开源许可证；分发许可、分支保护和后续可见性调整另按用户用途决定，当前不额外更改账户权限。

## 优先参考成熟方案，控制开发范围

遇到技术问题或计划新增能力时，先复用 docs/04 与 docs/research 的有效结论，再优先在 GitHub 定向检索成熟项目及其官方文档、Issues/Discussions、发布记录或已有修复。先确认现成方案能否解决当前问题，再决定适配或自研；不是等自行实现失败后才寻找参考。

判断依据包括需求匹配、维护情况、固定版本、测试与真实运行证据、许可证、接入及长期维护成本。星数、README宣传、源码中存在某个方法，都不能单独证明可用，更不能代替本项目G1等验收。

采用顺序为：复用已验证能力 → 做必要适配 → 对明确缺口作最小自研。将参考链接、固定版本、采用或不采用理由、剩余缺口记入对应研究记录或ADR。不能为了复用而引入不必要的大型框架、复制受限源码，或降低既有P0范围；简单明确的修复不重复进行大范围调研。

第19条约束执行成本：小改动只做必要检查，重要变更保留足够证据，不增加无意义文档、测试、依赖、重复调研或重复确认。优先更新现有记录；每个可验收单元仍同步受影响文档、PROJECT_STATUS、CHANGELOG，并检查敏感信息、提交推送及核对远端。

这些是后续开发与交付要求，不代表现有验证台已经具备一键环境自检、完整错误恢复或生产迁移能力；实际完成范围继续以状态与验证记录为准。

## 提交与审阅清单

- 需求编号、接口、目录格式变更必须更新对应文档；记录为何需要以及对用户行为的影响。
- 复用依赖先记录 commit、许可、采用方式、差距和真实验证证据；不将受限源码直接复制进仓库。
- 测试针对具体风险：跨页覆盖、置顶去重、中断恢复、部分失败、离线附件与路径安全；简单文档改动只做一致性和链接检查。
- 提交前查看 staged diff 和文件清单，防止 secrets、Cookie、含签名URL、数据库、媒体、原始日志误入Git；.gitignore不能替代检查。
- 同步后确认远端分支/commit确实存在，报告可访问的仓库/提交链接；不能仅凭命令启动或本地提交判断成功。
